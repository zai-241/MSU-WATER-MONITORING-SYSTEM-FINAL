## N1. An error reply from Firebase counts as success (medium)

**Where:** `backend/firmware/esp32_firmware.ino:2448` (command poll) and `:2869` (sensor upload); same lines in
`tank2/`, `tank3/`, `tank4/`.

Both places test `httpResponseCode > 0 && httpResponseCode != 401`, so **any** HTTP answer counts as success:
500 or 503 (Firebase busy or down), 429 (too many requests), a 3xx redirect. After such an answer the command poll:

1. calls `markCloudOk()`, so the 3-minute cloud watchdog thinks Firebase is fine and never restarts the ESP32;
2. parses the error text as the tank record. That text has no `"pumpOn"`, so `getBoolFromJson()` returns
   `false` (`:1193`). **While the pump is ON**, `false != lastSentPumpState` reads as an OFF command (`:2468`):
   the pump stops, the log says *"Manual pump OFF command accepted"*, and `pumpCommandResult` becomes `"accepted"`.
   Reports → Pump Activity Log then shows an OFF command that nobody sent.

The sensor upload has the same test: a 5xx counts as saved, so `lastSent*` is updated and the dashboard shows
`firebaseConnected: true` while nothing was stored.

**Failure scenario:** the pump refills Tank 1 and Firebase answers one poll with 503. The pump stops and the audit
log blames an operator. (Stopping is the safe direction, but the log is wrong and the refill is cut short.)

**Fix:** treat only `200–299` as success (as `flushRamLogBuffer()` and `logSystemEvent()` already do at `:817`
and `:910`). In the command poll, also skip the command logic when the payload does not contain `"pumpOn"`.

> **✅ Fixed in code (2026-11-20), all four sketches:** the command poll and sensor upload accept only 2xx, and
> commands are read only when the reply contains `"pumpOn"`. All four sketches compile for the ESP32 (91 % of flash);
> test `pumpSafety.test.tsx`. **Still to do:** upload the sketch to the Tank 1 ESP32.

## N2. No maximum pump run time (medium, safety)

**Where:** `processAutomaticPumpControl()` at `esp32_firmware.ino:2095–2196`, and `checkCloudWatchdog()` at `:596`.

Once the pump is ON it stops only at the overflow threshold, for a level-sensor fault, for maintenance, for
"Pump System" off, or by a command. Nothing checks how long it has run or whether the level is rising. A refill
pump with an empty source, a closed valve or a blocked pipe runs dry for as long as nobody notices. The cloud
watchdog also never restarts the controller while the pump is ON (`:596`), so the pump keeps running with no
internet and no one able to send OFF.

This mattered less while the pump was virtual; since 19 Nov a real relay and pump are wired on the Tank 1 drum.

**Fix:** stop the pump and log CRITICAL if (a) it has run longer than a set maximum (for example
`PUMP_MAX_RUN_MS`, sized for the 200 L drum), or (b) the level has not risen by at least 2–3 % within N minutes
of starting. Add a matching dashboard refusal or result text, and mention it in `docs/Methodology.md`.

> **✅ Fixed in code (2026-11-20), all four sketches:** a dry-run guard in `processAutomaticPumpControl()` stops the
> pump if the level has not risen 3 % (`PUMP_MIN_RISE_PERCENT`) within 10 min (`PUMP_NO_RISE_TIMEOUT_MS`), or after
> 60 min of running (`PUMP_MAX_RUN_MS`), in Auto and Manual mode. It logs CRITICAL, writes
> `tanks/{id}/pumpFault` (`"no-rise"` / `"max-run"`) and blocks automatic starts until an operator turns the pump
> ON from the dashboard (or the controller restarts). The alert engine raises "Pump Stopped: Check Water Supply"
> (`alert-{id}-pumpFault`, danger, so the worker sends a push), and the Dashboard card shows the reason. Details:
> `docs/Methodology.md` 4.1 item 4.
> **Still to do:** upload the sketch to the Tank 1 ESP32, then time a full refill (low → overflow) and set
> `PUMP_MAX_RUN_MS` to about 1.5 times that (and raise `PUMP_NO_RISE_TIMEOUT_MS` if the pump needs more than 10 min for
> 3 %, i.e. less than about 0.6 L/min on the 200 L drum). Deploy the web app so the Dashboard shows the notice;
> the worker picks up the new alert on its next Render deploy.

## N3. Manual pump mode works on Tank 1 only (medium)

**Where:** `pumpMode` is read only by `esp32_firmware.ino` (`:474`, `:2173`, `:2687`). `tank2/`, `tank3/`,
`tank4/` and every sketch made with `npm run firmware:new-tank` (copied from Tank 4) have no `pumpMode` code.
The Admin Panel switch (`frontend/src/pages/admin/Configuration.tsx`, "Pump mode") is system-wide and says
"Manual: only pump commands start the pump", with no word about Tanks 2+.

**Failure scenario:** an admin sets Manual, and a Tank 2 controller is installed later. Tank 2 still starts its
pump by itself at the low threshold, while the Admin Panel says it will not.

**Fix:** copy the `pumpMode` block (variables, the early `return` in `processAutomaticPumpControl()`, the
`/config` read) into the Tank 4 sketch, then into Tanks 2–3. Until then, add "(Tank 1 only for now)" to the
switch text.

> **✅ Fixed (2026-11-20):** the `pumpMode` code is in the Tank 2, 3 and 4 sketches (and so in new sketches made from Tank 4); they now differ from Tank 1 only in `TANK_ID`, the `tankId` on logs and the Tank 1 calibration print.

## N4. Pump command logged even when the write was refused (low)

**Where:** `confirmPumpToggle()` in `frontend/src/pages/Dashboard.tsx:500–520`.

`addLog({ action: 'PUMP_ON' / 'PUMP_OFF', details: 'Pump for … was turned ON' })` runs right after
`updateTank()` is called, not after it succeeds. If the database refuses the write (the pump lock was switched
on or the worker was unassigned while the confirm dialog was open, or the deployed rules differ from the code),
the dashboard shows the error, but `/logs` still records the command.

**Fix:** write the log in a `.then()` after `updateTank()` resolves (or log "command refused by the database"
in the `.catch()`).

> **✅ Fixed (2026-11-20):** the PUMP_ON / PUMP_OFF log is written only after the database accepted the command (`.then()` in `confirmPumpToggle()`).

## N5. Deleting an added tank leaves data and access behind (low)

**Where:** `deleteTank()` in `frontend/src/store/useStore.ts:759–769` removes only `tanks/{id}`.

Left behind:
- **Open alerts** `alert-{id}-…` in `/notifications`. The worker and the dashboards stop evaluating a deleted
  tank, so these are never resolved. Until someone acknowledges them they count as active, and the alarm
  sound keeps playing.
- **History** `/history/tanks/{id}`. A tank later registered with the same ID shows the old tank's history in Reports.
- **The device account** still has the `device` role, and the rules let a device write any `tanks/{id}`
  (`database.rules.json:49`). If that controller is still powered, its next upload (a PATCH) recreates the tank
  node with only sensor fields (no name or settings).

**Fix:** in `deleteTank()`, also resolve the tank's open alerts, and either delete or archive its history.
Warn in the delete dialog to disable the controller's device account (Admin Panel → Device Accounts).

> **✅ Fixed (2026-11-20):** `deleteTank()` now removes the tank, its `/history/tanks/{id}` and resolves its open `alert-{id}-…` records in one multi-path write (test in `defaultTanks.test.ts`). The delete dialog says to turn off the controller or remove its device account. No rules change was needed.

## N6. Worker restart during the night loses the slow-leak total (low)

**Where:** `nightStates` in `backend/worker/src/index.ts` is kept in memory only. On a restart (a Render redeploy
after a push to `main`, or a crash) `evaluateNight()` starts a fresh state for the same window, with
`committedDrop: 0` (`frontend/src/lib/alertEngine.ts:520–528`).

**Failure scenario:** a 2 % drop before a 1 AM redeploy and a 2 % drop after it are each below the 3 % threshold,
so no "Possible Slow Leak" is raised for a 4 % loss. The fast check ("Possible Leak or Open Faucet") is not
affected beyond its 30-minute look-back.

**Fix:** avoid pushing to `main` during 10 PM–3 AM. A full fix would save the night state to the database
(for example `/system/nightWatch/{id}`) and reload it on start.

> **✅ Fixed (2026-11-20):** the worker saves the night state to `/system/nightWatch` (at most once a minute and on stop) and reloads it on start (`restoreNightState()` in `alertEngine.ts`; tests in `nightWatch.test.ts`). Only the worker (Admin SDK) writes there.

## Checked and found fine

- **Night watch window maths** (`nightWindowAt`, UTC+8, crossing midnight). Equal start and end hours are refused
  by the Admin Panel form, and missing settings fall back to the defaults.
- **Live calibration limit.** The browser uses server time, the rules cap `calibrationUntil` at now + 31 min, and
  the firmware stops by itself after 30 min.
- **Per-tank maintenance.** Only admins can change it (rules `:66–68`). The worker and browsers skip alerts and
  the offline watchdog for it, and the ESP32 refuses ON commands while it is on.
- **Presence.** The server removes entries on disconnect, they are removed before sign-out, and only admins can read them.
- **Pump switch permissions.** The dashboard's `canTogglePump` (`Dashboard.tsx:70`) matches the database rule for
  workers (assigned tank, lock off).
- **Default tanks.** Tanks 1–4 are re-created only from a live database snapshot and never overwrite an existing tank.
